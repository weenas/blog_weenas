## 一封邮件，开发线停摆

2026 年 11 月 2 日上午 10:54，收到 Anthropic 的邮件：账号被停用，理由是自动系统检测到大量违反使用政策的信号，已经过人工复核。当天我的使用量屈指可数，完全不知道触发了什么。中午提交申诉，下午 13:35 收到回复：不予恢复，依然没有给出任何具体原因。

账号本身倒没什么可惜的，可惜的是工作流：我手头一个开源项目的开发主力是 Claude Code，号没了，线就断了。申诉这条路走不通，只能想办法重新订一个。

## 先盘点手里有什么牌

Claude 不对中国大陆提供服务，国内 IP 打开 claude.ai 只有一个「你所在的地区暂不可用」的页面，连注册入口都没有。所以订阅这件事，拼的是四样东西：出口 IP、支付卡、账单地址、验证手机号，最好同属一个受支持的国家地区。

我手里的牌凑一凑：有一张泰国银行的 Visa 借记卡、一个泰国地址、一张泰国运营商的预付费电话卡，另外还有一台美国 VPS。

最初的设想是全套泰国方案：泰国 SIM 开了数据漫游，漫游流量的出口一般在泰国，正好凑齐「泰国 IP + 泰卡 + 泰国地址 + 泰国号码」。结果卡在第一步：手机明明显示 4G，却打不开任何网页——漫游数据多半还差一个单独的漫游数据包，运营商那一侧没有可用数据，光在手机里打开漫游开关没用。

于是改方案：注册走美国 VPS 的出口（美国是受支持地区，IP 固定、归属明确），付款用泰国卡。当天下午，新账号注册完成，进入付款环节——然后开始了连环坑。

## 坑一：银行卡被拒绝，但银行说没这回事

在结账页填好泰卡，提交，红色提示：「您的银行卡被拒绝了。」

第一反应是查银行：银行 App 里，线上消费和境外消费的锁都是开着的（泰国银行近来对新卡默认锁定这两类消费，算是个常见坑，但我不是这个情况）；更关键的是，**交易记录里根本没有这笔失败记录**。

这条信息价值很大：它说明扣款请求压根没到银行，拒绝发生在更靠前的一层——Stripe 的风控。泰国发行的卡 + 美国机房 IP + 全新账号，这个组合在风控眼里就是高风险画像，请求在到达发卡行之前就被拦下了。这种情况，再怎么调整银行卡设置都没用。

中间还穿插了一个小插曲：第一次尝试时我用了 Chrome 无痕模式，报的是另一句错——「我们无法验证您的浏览器」。无痕模式默认拦截第三方 Cookie，而 Stripe 的验证和银行的 3D Secure 跳转恰恰依赖跨站 Cookie 和 iframe，一拦就跑不通。换成普通窗口，这个错误消失，才走到了真正的拒卡环节。

还有个细节：结账页的账单国家列表里没有中国（只列受支持地区），而我的卡在银行预留的地址偏偏是中国地址。账单国家的正确填法是按**发卡国家**选，也就是泰国，配泰国地址。银行预留地址是哪儿的，Stripe 并不真的核对。

结论：卡这条路在 Stripe 这里走不通，换通道。

## 坑二：苹果加卡，两连错

Claude 的 iOS App 订阅走苹果支付，可以绕开 Stripe。为此我新注册了一个泰国区 Apple ID（地区选泰国，用泰国号码验证），卡是泰国卡，理论上完美自洽。实际连错两次：

第一次：「The payment card number you entered is not a valid payment card number.」——这个纯属手误，卡号输错了一位，重输就过了。

第二次：「Cannot Add Payment Method.」号码过了，卡在验证。查银行 App，依然没有苹果发来的验证记录——又是没到银行的一层。原因是账单地址：泰国区账户加卡，账单地址必须是泰国地址，我填的是银行预留的中国地址，苹果自己的校验直接拦下，根本不会去问银行。

## 柳暗花明：话费支付

在泰国区 Apple ID 添加付款方式的界面里，除了银行卡，还有一个选项：手机支付（运营商代扣，Direct Carrier Billing）。原理是订阅费直接扣话费——后付费记账单，预付费扣余额，跟银行卡没有关系。

剩下的问题是钱怎么进话费：银行 App 可以给这个号码充值，存款账户直接扣款。整条链就此打通：**银行卡 → 话费余额 → 苹果代扣 → Claude 订阅**，全程不跟 Stripe 的风控和苹果的银行卡验证打交道，支付画像反而是全泰国一致的。

不过运营商代扣有额度规则。运营商官方的限额表里，预付费号码的代扣单笔上限很低，大约 ฿1,200 这一档。对照价格：Claude Pro 在泰国区是 ฿699/月，一笔能过；Max 的价格高得多，单笔必然超限，余额再多也扣不了。所以先订 Pro，Max 以后再说（转后付费或者打通银行卡路线）。

最后一步还闹了个小乌龙：我先往话费里充了 ฿700，仍然提示余额不足——代扣的可用额度并不完全等于账面余额；又补了一笔，才订阅成功。

## 尾声：虚惊一场的「记忆丢失」

新号订好，在 Mac 上登录 Claude Code，第一反应是：之前的记忆怎么不见了？

查了一圈，是虚惊。Claude Code 的记忆存在本地 `~/.claude/projects/` 下面，按项目目录组织，跟账号没有关系，换号登录不会动它。看不到纯粹是因为打开的目录不对——必须在项目根目录启动，它才加载对应项目的记忆。真正丢掉的只有 claude.ai 云端的对话历史和云端记忆，那些绑在被封的旧号上，找不回来了。

顺带一提，那条写了几个月代码的旧会话转录文件已经有 471MB 了。本地数据无价，备份这件事得提上日程。

## 复盘

一下午折腾下来，沉淀了几条还算通用的经验：

1. **支付失败要分层定位**：浏览器（Cookie/验证）→ 支付网关风控（Stripe Radar）→ 收单/苹果校验 → 发卡行。最有用的诊断动作是看失败记录出现在哪一层：银行 App 里查无记录，就说明请求没到银行，别在银行卡设置里浪费时间。
2. **地区一致性是订阅类服务的隐形门槛**：IP、发卡国、账单地址、商店区域，能对齐的尽量对齐；对不齐的地方，就是被风控的点。
3. **无痕模式不适合走支付流程**：它挡得住本地 Cookie，挡不住指纹，却能实打实地破坏 3DS 验证。
4. **运营商代扣是正经支付通道**：在卡支付走不通的时候，话费支付 + 银行充值这条曲线链路，画像干净、成功率高，缺点是额度上限低。
5. **工具的数据要分清本地还是云端**：本地的（Claude Code 的记忆和会话）换号不丢，值得备份；云端的随账号生死，重要内容要导出。

订阅已经恢复，每月续费靠话费余额，我给每月 28 号设了个充值提醒——这条用「话费续命」的会员，大概也是没谁了。

还有一件待办记在这儿：下次去泰国，必须去银行把预留地址改成泰国地址。这次的好几个坑，追根究底都和这个中国地址有关，能改掉就少很多麻烦。

至于这个新号能坚持多久，我心里也没底。能做的只有把使用方式尽量放规矩：固定出口、正常付费、本地数据勤备份。希望这次不要再被封控了。
